# P3.08 vs P3.08-DIST: Single-Machine vs. Distributed Rendering

> **Naming note:** this file's name retains "P3_09" for historical reasons
> (it predates the naming-collision fix). The distributed-render subsystem
> described here is **not** phase P3.09 — phase P3.09 is canonical
> Automated QA (`qa.ts` / `runP309QA` in `pipeline.ts`), a separate,
> unrelated module. See the naming note at the top of
> `pipeline3_production/src/orchestration_p309.ts` for the full context.

## Canonical Relationship

**P3.08 Remotion (single-machine render)** is the PRIMARY production path.

**P3.08-DIST Distributed Kaggle Orchestration** is an OPTIONAL optimization variant.

P3.08-DIST does NOT replace P3.08; it orchestrates multiple P3.08-like renders across distributed workers.

```
P3.08: Remotion (30 FPS, H.264, AAC audio) → MP4 file
  ↑
  └─── Single machine, all elements composed in memory, deterministic output
  
P3.08-DIST: Orchestration (distributed Kaggle workers) → coordinates multiple Remotion renders → merges shards via FFmpeg → MP4 file
  ↑
  └─── Sharding strategy for very large videos or parallel render optimization
```

---

## P3.08: Single-Machine Render (Primary Path)

**When to use:** Standard production (most videos < 3 minutes, standard resource load)

**What it does:**
1. Reads ProductionPackageHandoff (scenes, shots, prompts, audio, decision log)
2. Reads user-provided visual assets (images + silent videos ≤10s)
3. Reads system-managed assets (music, SFX, captions, motion metadata)
4. Composes all elements into a single Remotion timeline
5. Renders at 30 FPS, H.264 video + AAC audio
6. Outputs: one MP4 file (frozen, ready for delivery)

**Characteristics:**
- Synchronous (one video per execution)
- Deterministic (same inputs → same output, frame-for-frame)
- Predictable resource use (memory, CPU, time)
- No distribution complexity
- Single point of failure (if render fails, re-run entire video)

**Architecture (P3.08 frozen module):**
```
├── Input: ProductionPackageHandoff + visual assets
├── P3.01 Ingest: Validate structure
├── P3.02 Validation: Schema + type checking
├── P3.03 Asset Matching: Link shots to visual assets
├── P3.04 Voice: Generate Piper preview
├── P3.05 Voice: (optional) ElevenLabs production
├── P3.06 Timing: Compute shot durations (frames)
├── P3.07 Timeline: Build ordered entries with motion metadata
├── P3.08 Render: Remotion composes + renders at 30 FPS
└── Output: MP4 file (H.264 + AAC)
```

**Example:** 180-second Turkish philosophy video
- Input: 28 visual assets (user images + 2 silent videos) + 180s narration + music/SFX
- Process: ~5-15 minutes rendering (depending on hardware)
- Output: 180s MP4, 1GB file, ready for YouTube upload

## P3.08-DIST: Distributed Kaggle Orchestration (Optional Variant)

**When to use:** Very large videos (>10 minutes), parallel render optimization, or experimental distributed workflow

**What it does:**
1. **Phase 1 — Planning:** Analyzes timeline, determines optimal shard boundaries
2. **Phase 2 — Assignment:** Distributes shards to available workers + resource budgeting
3. **Phase 3 — Execution:** Each worker renders its shard (parallel P3.08-like Remotion render)
4. **Phase 4 — Merge:** Combines shards via FFmpeg (video concatenation)
5. **Phase 5 — QA:** Validates merged output (continuity, audio sync, duration)

**Characteristics:**
- Asynchronous (multiple workers render in parallel)
- Sharded (large video divided into manageable chunks)
- Experimental (not frozen; may be optimized or replaced)
- Complex orchestration (worker assignment, shard overlap handling)
- Partial failure handling (re-run failed shard, not entire video)

**Architecture (P3.08-DIST NOT frozen, may evolve):**
```
├── Phase 1 Planning: timeline shard strategy (frame ranges per worker)
├── Phase 2 Assignment: worker allocation + cost estimation
├── Phase 3 Execution: parallel Remotion renders (one per shard, isolated)
│   ├── Worker A: frames 0-2000 → shard_a.mp4
│   ├── Worker B: frames 2000-4000 → shard_b.mp4
│   └── Worker C: frames 4000-6000 → shard_c.mp4
├── Phase 4 Merge: FFmpeg concatenation (shard_a + shard_b + shard_c → final.mp4)
└── Phase 5 QA: Validate continuity, audio sync, duration

Output: MP4 file (same spec as P3.08)
```

**Example:** 30-minute webinar video
- Input: 50+ visual assets, 30min narration, music/SFX
- Sharding: 6 workers × 5-minute shards (avoid single machine bottleneck)
- Parallel render: ~5-10 minutes (6× speedup, minus merge overhead)
- Merge: ~2 minutes (FFmpeg shard concatenation)
- Output: 30min MP4, 8GB file, ready for delivery

## Key Differences

| Aspect | P3.08 (Remotion) | P3.08-DIST (Distributed) |
|--------|------------------|-------------------|
| **Status** | Frozen (production-ready) | Experimental (may evolve) |
| **Scaling** | Single machine (standard videos) | Multiple workers (very large videos) |
| **Render Time** | Linear (time ∝ video length) | Parallel (time ∝ video length / worker count) |
| **Complexity** | Low (one process) | High (orchestration, shard management) |
| **Failure Handling** | Re-run entire video | Re-run failed shard only |
| **Determinism** | Fully deterministic | Deterministic per shard, merge is deterministic |
| **Use Case** | Most production videos | Optimization for large/batch render |
| **Dependencies** | Remotion, FFmpeg | Remotion, Kaggle API, FFmpeg |

## P3.08-DIST Does NOT Replace P3.08

**Never choose P3.08-DIST because:**
- "P3.08 might fail" (P3.08 is proven, frozen; P3.08-DIST is experimental)
- "P3.08 is too slow" (single-machine render scales fine for <3 min videos, standard use case)
- "We want distributed" (distribution only helps >10min videos; premature optimization)

**Only choose P3.08-DIST when:**
- Video is genuinely very large (>10min, >50 scenes, resource-intensive effects)
- Batch rendering multiple large videos (parallelization saves wall-clock time)
- Experimental workflow requirements explicitly ask for distributed execution
- Research/analysis on distribution benefit completed

## Frozen Module Boundary (P3.08 only)

**P3.08 (FROZEN — no changes without defect proof):**
- Input validation (P3.01-P3.06)
- Remotion render logic
- Output MP4 specification (H.264 + AAC)

**P3.08-DIST (NOT frozen — may optimize, refactor, or replace):**
- Sharding strategy
- Worker assignment
- Phase orchestration
- Merge validation

If a defect is found in P3.08, escalate with:
1. Reproduction case
2. Regression test proving defect
3. Minimal patch (no architectural change)
4. The pipeline's full test suite passing (run `npm test` in pipeline3_production; see FULL_PIPELINE_CANONICAL_MANIFEST.md for the current count)

## Production Decision Tree

```
Video length?
  ├─ < 3 minutes → use P3.08 (standard, proven)
  ├─ 3-10 minutes → use P3.08 (single machine adequate)
  ├─ > 10 minutes, research render time → use P3.08 first, benchmark
  │   ├─ Acceptable render time (< 30 min) → stay with P3.08
  │   └─ Unacceptable render time (> 30 min) → evaluate P3.08-DIST opt-in
  └─ Batch workflow (20+ large videos) → consider P3.08-DIST for parallelization

Use P3.08-DIST?
  ├─ No → proceed with P3.08
  └─ Yes → ensure Kaggle credentials configured + cost budget approved
```
